## Part A — The 60-second mental model

The agent never troubleshoots. It only needs to answer one question: **"Which
KB article is this user talking about?"** This service answers that. It is a
**two-stage search engine**:

1. **Retrieve (pgvector):** turn the user's words into a vector of numbers
   (an *embedding*) and find the KB articles whose text is closest in meaning —
   plus a keyword match — then merge both into a shortlist.
2. **Re-rank (Cohere):** take that shortlist and let a more powerful model read
   the query and each candidate *together* to produce a precise 0–1 relevance
   score, giving the final order.

Then a small **decision engine** looks at the top score and the gap to #2 and
decides: **resolve** (confident, present the article), **ask a follow-up**
(unsure — get one more detail), or **conclude no match** (nothing fits).

That decision engine is the *same logic* the original Azure AI Search version
used — we only swapped the search technology underneath (AI Search → pgvector +
Cohere), keeping the contract and behaviour identical.

## Part B — The data model (what we store, and why)

### What we embed
Real KB documents have **no uniform "Symptoms" field**. What a user actually
describes is the **heading**, the **user-experience / question**, and sometimes
the **cause** — never the fix. So from each `.docx` we keep only:

| Field | Example (KB0010265) | Used for |
|---|---|---|
| `title` (heading) | "Outlook Performance Troubleshooting" | matching |
| `question` (User Experience / Questions) | "the loading screen is stuck until an error message" | matching |
| `cause` | "Outlook's processes are stuck, or the OST file is corrupted" | matching |
| `environment` | "Windows 10/11, O365" | metadata (not embedded) |
| Resolution / Options | Task Manager, Safe Mode… | **discarded** |

Rationale: indexing the fix text adds noise (every doc says "click", "OK",
"Control Panel") and blurs the signal. Matching lives in title + question + cause.

### "Chunking" = one row per field
Because the useful text per doc is only a few lines, a "chunk" here is a **single
field**, not a sliding window of tokens. Each non-empty field becomes one row we
can search. A title-only doc (e.g. KB0013608) becomes exactly one row. Several
rows share the same `kb_id`; after searching we collapse back to distinct
articles.

### Two database tables
- **`kb_articles`** — one row per article: `kb_id`, `title`, `question`,
  `cause`, `environment`, `guidance_troubleshoot`, `embed_text` (title+question+
  cause, used for reranking).
- **`kb_chunks`** — one row per field: `kb_id`, `field_type`
  (`title`/`question`/`cause`), `content`, `embedding` (the 1536-number vector),
  `tsv` (a full-text index of the content, auto-generated by Postgres).

## Part C — File-by-file logic

Files live in `vinny-no-ai-search/`. The runtime code is in `app/`.

### Runtime pipeline (what serves live traffic)

#### `app/config.py` — central configuration
- Single place that reads **every** setting from environment variables (which on
  Azure come from the App Service "Application settings").
- **Secrets** (`PG_CONN` = the Postgres connection string, `TEVA_AI_KEY` = the
  Azure AI key shared by embeddings + Cohere) are resolved by `get_pg_conn()` /
  `get_ai_key()`: **environment variable wins**, otherwise it falls back to
  **Azure Key Vault** (`vinny-kb-tool-vault1`). The Key Vault import is lazy and
  wrapped in try/except, so if the SDK isn't installed (our lean deployment) it
  silently uses the env var.
- Holds the embedding endpoint/model, the Cohere endpoint/deployment/route, the
  retrieval knobs (`VECTOR_K`, `KEYWORD_K`, `RRF_K`, `RETURN_K`, `RERANK_K`), the
  0–1 **score bands** (`CONFIDENT_SCORE`, `MIN_DISPLAY_SCORE`, `FOLLOWUP_FLOOR`,
  `SPREAD_THRESHOLD`), the follow-up thresholds (`MIN_FIELD_SCORE`,
  `TOP_FIELDS_K`), the round cap (`MAX_ROUNDS`), and optional API-key auth.
- **Why it matters to the client:** every behaviour knob is here and overridable
  without code changes.

#### `app/kb_parser.py` — turn `.docx` into clean records
- A `.docx` is a zip of XML; we read `word/document.xml` directly with the Python
  standard library — **no Microsoft Office dependency**.
- `parse_doc()` extracts `kb_id` (from "KB ID:" or the filename), the `title`
  (first line, minus the "(GLOBAL)" tag), then walks the body collecting text
  into the **`question`** and **`cause`** buckets, **stopping** the moment it hits
  a Resolution / Answers / Options / Note header (those are dropped).
- Handles the real-world messiness: the user-facing field may be labelled "User
  Experience" *or* "Questions"; "Cause" may be absent; a doc may be title-only.
- `KBDoc.fields()` returns the non-empty `(field_type, content)` pairs (the rows
  to embed). `KBDoc.embed_text()` returns "title. question. cause" (the text sent
  to the reranker).
- **Role:** the *only* place that decides what content enters the system.

#### `app/text_utils.py` — text normalization
- One shared pipeline: lower-case → fold known multi-word phrases (e.g. "loading
  screen") → tokenize → drop stopwords and the ever-present word "outlook" →
  **Porter-stem** (so "crashes"→"crash", "loading"→"load").
- Used by `followup.py` to compare the user's words to a candidate's phrases.
- Stemming uses `nltk`'s PorterStemmer (needs no downloaded data); if `nltk` is
  missing it falls back to a tiny suffix stemmer, so the service always starts.

#### `app/embeddings.py` — Azure OpenAI `text-embedding-3-small`
- `embed_texts([...])` sends text to the embedding model and gets back one
  **1536-number vector** per input, then **L2-normalizes** each (so cosine
  similarity equals a plain dot product, and the numbers behave like a 0–1
  relevance signal).
- `embed_query()` is the single-string helper used at request time.
- `to_pgvector()` formats a vector as the `'[0.1,0.2,…]'` literal Postgres/pgvector
  expects.
- Uses only the Python standard library for HTTP (no extra dependency).
- **Role:** the "meaning encoder" — turns words into geometry so similar meanings
  sit close together.

#### `app/db.py` — Postgres connection helper
- Opens **one** psycopg2 connection for the process (the service runs a single
  worker), in autocommit mode, and **reconnects transparently** if the connection
  drops.
- `fetch_all()` / `execute()` are thin query helpers.
- Connection string comes from `config.get_pg_conn()` (Key Vault / env).

#### `app/schema.sql` — the pgvector database schema
- Enables the `vector` (pgvector) and `pg_trgm` extensions.
- Creates `kb_articles` and `kb_chunks` (see Part B).
- Creates two indexes on `kb_chunks`:
  - **HNSW** on `embedding` (`vector_cosine_ops`) → fast approximate **vector**
    search.
  - **GIN** on `tsv` → fast **keyword** (full-text) search.
- **Role:** defines the storage and the two search "legs".

#### `app/retrieval.py` — hybrid search (the pgvector stage)
The heart of stage 1. `hybrid_search(query)` does:
1. **Embed** the query (via `embeddings.embed_query`).
2. **Vector leg** (`_vector_leg`): `ORDER BY embedding <=> query LIMIT VECTOR_K`
   — the top ~30 chunks by cosine similarity. Returns each chunk's cosine.
3. **Keyword leg** (`_keyword_leg`): `WHERE tsv @@ websearch_to_tsquery(query)`
   ranked by `ts_rank_cd` — the top ~30 chunks by lexical overlap.
4. **RRF fusion**: combine the two ranked lists with **Reciprocal Rank Fusion** —
   each chunk gets `score = Σ 1/(RRF_K + rank)` across the lists it appears in
   (`RRF_K=60`). RRF needs no score normalization between the legs, which is why
   it's the standard way to merge a keyword list and a vector list.
5. **Aggregate to articles**: keep the best chunk score per `kb_id`, attach the
   article's `title`/`question`/`cause`/`embed_text`, and return the top
   `RERANK_K` (~10) distinct articles, sorted by fused score. It also carries the
   best **cosine** per article (used as the fallback score if Cohere is off).
- **Role:** narrows the whole KB down to a small, high-recall shortlist.

#### `app/rerank.py` — Cohere Rerank v4 (the reranking stage)
- `rerank(query, documents, top_n)` sends the query + candidate texts to the
  **Cohere cross-encoder** and returns `[(index, relevance_score 0–1), …]`
  best-first.
- **Config-driven route** (`RERANK_ENDPOINT` / `RERANK_PATH` /
  `RERANK_API_VERSION` / `RERANK_AUTH_STYLE`) because the exact Foundry REST path
  for Cohere v4 is set per environment.
- **Graceful fallback:** if reranking is disabled or the call fails, it returns
  `None` (logged once) and the caller uses the embedding **cosine** as the score,
  so the service keeps working with slightly less precise ordering.
- **Role:** the "precision" step — see Part E.

#### `app/followup.py` — grounded follow-up selection
- When the tool is *unsure* (spread "high"), it must ask a smart question. This
  module picks the best phrase to ground that question in.
- For each top candidate it forms phrases from its `question` + `cause` (or the
  `title` if title-only) and scores each phrase:
  - `rel` = cosine similarity between the **user's description** and the phrase
    (using `text_utils` stemmed word vectors) — *is this phrase relevant to what
    the user said?*
  - `mass` = the share of candidate score carrying the phrase; `dist =
    1 − |2·mass − 1|` — *does this phrase split the candidates (peaks at ~50%)?*
  - `final = 0.5·rel + 0.5·dist`.
- Keeps phrases scoring ≥ `MIN_FIELD_SCORE` (drops near-duplicates), up to
  `TOP_FIELDS_K`. **If none clears the bar, it returns `[]`** → the agent is told
  to ask its own follow-up (freeform).
- This is a faithful port of the original service's discriminating-symptom logic,
  now over heading/cause/question instead of a "symptoms" field.

#### `app/main.py` — the FastAPI service and decision engine
- Builds the FastAPI `app` and exposes three endpoints:
  - **`POST /get_kb_candidates`** — the tool the agent calls.
  - **`POST /debug_search`** — diagnostic (ranked list + scores + selected
    phrases); the agent never calls it.
  - **`GET /healthz`** — liveness + article count.
- **Round tracking:** an in-memory counter per `session_id` (`_bump_round` /
  `_clear_round`) so a conversation can't loop forever (`MAX_ROUNDS`). This is why
  the service runs a **single worker** — the counter lives in the process.
- **`compute_spread(scores)`** — returns `"high"` when there is **no clear
  winner**: either the top score is below `CONFIDENT_SCORE` (*weak absolute*) or
  the gap to #2 is below `SPREAD_THRESHOLD` (*weak dominance / near-tie*).
  `"low"` = a confident, clear winner.
- **`_score_candidates(query, candidates)`** — calls Cohere rerank; if available,
  assigns the 0–1 relevance and re-orders; otherwise assigns the cosine
  (fallback). This produces the authoritative `top_score`.
- **`get_kb_candidates` routing** (Part F) — decides resolve / follow-up /
  conclude and returns the contract.
- **Role:** orchestrates the pipeline and makes the final decision. **This is the
  brain; the search technology is swappable underneath it.**

### Building & tuning the index (offline, not live traffic)

#### `app/ingest.py` — build the pgvector index
- The offline job: parse every `.docx` → get its fields → **embed** them in a
  batch → **upsert** into `kb_articles` + `kb_chunks`.
- **Idempotent:** re-running rebuilds each article's chunks (delete + insert), so
  editing a doc and re-running is safe. The live service reads the DB, so **no app
  restart** is needed after re-ingest.
- Run with `--recreate` to drop/recreate the tables first.

#### `app/calibrate.py` — measure accuracy & recommend thresholds
- Runs the **full live pipeline** over the labelled gold set
  (`vinny-ai-search/eval/gold_set.json`, read-only) and reports **top-1**,
  **recall@K**, and **MRR**, plus the score gap between correct in-KB hits and
  out-of-KB queries — which is what `CONFIDENT_SCORE` / `MIN_DISPLAY_SCORE` should
  sit between.
- Current result (cosine mode): **top-1 95.9%, recall@3 100%, MRR 0.975.**
- Re-run whenever docs change or after enabling Cohere rerank.

### Observability (tracing, like `teva-kb-trace`)

#### `app/trace_kit.py` — the tracing engine
- Collects every step of one request into a single ordered block and writes:
  `trace_<date>.log` (readable), `trace_<date>.jsonl` (machine), and one
  **per-turn file** under `turns/` grouped by `session_id`.
- Files land under `TRACE_LOG_DIR` (`/home/LogFiles/kbtrace` on Azure), viewable
  in Kudu.

#### `app/main_traced.py` — the traced entry point
- Imports `main.py` **unchanged** and wraps every stage (embedding, vector leg,
  keyword leg, RRF, scoring, spread, follow-up) plus an HTTP middleware, so each
  call produces a human-readable, step-by-step trace. Also serves a browser
  viewer at `/trace?key=<TRACE_VIEW_KEY>`.
- The deployed app runs `app.main_traced:app`. To run without tracing, point the
  startup at `app.main:app` — identical behaviour, no trace files.

### Configuration & packaging files
- **`requirements.txt`** — runtime dependencies (fastapi, uvicorn, pydantic,
  psycopg2-binary, nltk; azure-identity/keyvault are optional, for the Key Vault
  path).
- **`startup.sh`** — the uvicorn start command (single worker).
- **`runtime.txt`** — pins Python 3.12.
- **`.env.example`** — every setting documented for local runs / handoff.
- **`openapi/kb_candidates.json`** — the OpenAPI 3.0 contract the Foundry agent
  imports to call `get_kb_candidates`.
- **`data/*.docx`** — the 8 source KB articles (the source of truth for content).
- **`README.md`** — the quick architecture overview (this file is the deep dive).

## Part D — The role of **pgvector**

**pgvector** is a PostgreSQL extension that lets a normal SQL database store
**vectors** (lists of numbers) and search them by similarity. In this system it
plays two roles:

1. **The store.** Every KB field's embedding (1536 numbers) lives in the
   `kb_chunks.embedding` column, alongside the text and a full-text index. One
   database holds everything — no separate search service.
2. **The retriever (stage 1).** Given the query's embedding, pgvector's **HNSW
   index** finds the nearest chunks by **cosine distance** (`<=>`) in
   milliseconds — this is *semantic* search (matches meaning, not just words).
   The same table's **full-text index** provides the *keyword* leg. We fuse both.

Why it's the right choice here: it's **cheap** (runs in a small Postgres you may
already have — no per-query search-service fee), **all-in-Azure** (Azure Database
for PostgreSQL), and **accurate** (semantic + keyword hybrid). It replaces Azure
AI Search's vector index + keyword index in one place.

**Analogy for the client:** pgvector is the *librarian who fetches the ~10 books
most likely to be about your topic* — fast and broad, so the right one is almost
always in the stack.

## Part E — The role of **Cohere reranking**

pgvector is fast but judges each field in isolation (query-vector vs
field-vector). **Cohere Rerank v4** is a **cross-encoder**: it reads the query
and a candidate article **together** and outputs a single **0–1 relevance
score**. That joint reading is far more precise at separating look-alike
candidates (e.g. "won't open" vs "stuck on loading" vs "crashes on calendar").

How it's used: after pgvector returns ~10 candidates, `rerank.py` sends the query
+ each candidate's `title+question+cause` to Cohere, which returns the best order
and the **top score that drives the routing decision** (Part F). Everything stays
in Azure (Cohere is deployed on the Azure AI Foundry account), which satisfies
strict data-residency requirements.

**Two-stage pattern (retrieve → re-rank):** pgvector maximizes *recall* (don't
miss the right article); Cohere maximizes *precision* (put it exactly first).
This is the standard production RAG/search pattern.

**Current status:** the exact Cohere REST route on the Foundry endpoint is a
pending config item, so the service runs in **cosine-fallback mode** (uses the
pgvector cosine as the score). Even so it scores **top-1 95.9% / recall@3 100%**.
Enabling Cohere (set `RERANK_PATH`/`RERANK_API_VERSION`) tightens the top-of-list
ordering; no code change is needed.

**Analogy for the client:** if pgvector is the librarian who fetches 10 candidate
books, Cohere is the *expert who reads your exact question and each book's summary
side-by-side and ranks which one truly answers you.*

## Part F — Scoring bands and the routing decision

Everything runs on a **0–1** relevance scale (Cohere's scale, or cosine in
fallback). Four thresholds (all in `config.py`, tuned on the gold set):

| Threshold | Default | Meaning |
|---|---|---|
| `CONFIDENT_SCORE` | 0.60 | at/above **and** a clear winner → **resolve**. Set above the out-of-KB ceiling (~0.54) so off-topic queries can't auto-resolve. |
| `SPREAD_THRESHOLD` | 0.10 | if top − #2 is smaller than this, it's a near-tie → **don't resolve**, ask. |
| `FOLLOWUP_FLOOR` | 0.15 | below this there's no usable signal → skip phrase selection, go freeform. |
| `MIN_DISPLAY_SCORE` | 0.40 | at the round cap, present the best article only if it clears this; else conclude no-match. |

`compute_spread` returns **"high"** (ambiguous) if the top is below
`CONFIDENT_SCORE` **or** the gap to #2 is below `SPREAD_THRESHOLD`; otherwise
**"low"** (clear winner).

The endpoint then follows exactly this order:
1. **RESOLVE** — `top_score > CONFIDENT_SCORE` **and** spread `low` → return the
   `kb_id`. Done.
2. **ROUND CAP** — if this is the `MAX_ROUNDS`-th call for the session → stop
   asking: present the best article if `top_score ≥ MIN_DISPLAY_SCORE`, else
   return `kb_id = null` (no match).
3. **ASK, GROUNDED** — otherwise, if `top_score ≥ FOLLOWUP_FLOOR` and a
   heading/cause/question phrase is relevant → return those phrases in
   `discriminating_symptoms` for a targeted question.
4. **ASK, FREEFORM** — otherwise → empty `discriminating_symptoms` + a message
   telling the agent to ask its own focused Outlook follow-up.

## Part G — The full end-to-end flow (agent → answer)

```
 User: "Outlook keeps freezing when it opens"
   │
   ▼
 Classification Agent (Azure AI Foundry)
   │  builds a clean cumulative description + a stable session_id
   │  HTTP POST /get_kb_candidates   {description, session_id}
   ▼
 ┌─────────────────────── this service (main.py) ───────────────────────┐
 │ 1. _bump_round(session_id)            count this conversation's rounds │
 │ 2. retrieval.hybrid_search(description):                               │
 │      a. embeddings.embed_query  → 1536-dim vector (Azure OpenAI)       │
 │      b. pgvector VECTOR leg     → nearest chunks by cosine (HNSW)      │
 │      c. Postgres KEYWORD leg    → chunks by full-text match            │
 │      d. RRF fuse (b)+(c)        → merge rankings                       │
 │      e. dedupe to articles      → ~10 distinct candidates              │
 │ 3. _score_candidates:                                                  │
 │      Cohere rerank the ~10 (query+text together) → 0–1 scores          │
 │      (or cosine fallback) → final order + top_score                    │
 │ 4. compute_spread(scores)       → "low" (clear) or "high" (ambiguous)  │
 │ 5. ROUTE:                                                              │
 │      • confident + clear   → RESOLVE  {followup_required:false, kb_id} │
 │      • at round cap        → present best OR {kb_id:null}              │
 │      • ambiguous + relevant→ ASK grounded {discriminating_symptoms:[…]}│
 │      • ambiguous, nothing  → ASK freeform {discriminating_symptoms:[]} │
 └────────────────────────────────────────────────────────────────────────┘
   │  JSON response
   ▼
 Agent reads the response:
   • followup_required=false, kb_id set   → present that KB article; done.
   • followup_required=false, kb_id=null  → close / hand off.
   • followup_required=true, phrases      → ask ONE question grounded in them,
                                            then call again (SAME session_id)
                                            with the fuller description.
   • followup_required=true, no phrases   → ask its own Outlook follow-up, call again.
```

**A concrete two-round example (real trace):**
- Round 1 — "outlook not responding": top candidate 0.669, but #2 is 0.633 → gap
  0.036 < 0.10 → **spread high** → ambiguous. No single phrase is relevant enough
  → **ASK freeform**. The agent asks "What happens when you open it?"
- Round 2 — "outlook not responding, stuck on loading screen with an error":
  top candidate **KB0010265 @ 0.789**, clear winner → **RESOLVE**. The agent
  presents KB0010265.

Both rounds share `session_id`, so they appear in **one** trace turn file, and
the round counter guarantees the loop ends by `MAX_ROUNDS`.

## Part H — The response contract (`POST /get_kb_candidates`)

Request: `{ "description": "<full cumulative text>", "session_id": "<stable id>" }`

Response fields, read in this order:

| Field | Meaning |
|---|---|
| `followup_required` | `true` → ask one more question and call again; `false` → done. |
| `kb_id` | the matched article (when `followup_required=false` and confident); `null` when concluded with no match. |
| `top_score` | confidence of the top candidate, 0–1. |
| `discriminating_symptoms` | when `followup_required=true`: phrases (from heading/cause/question) to ground the next question in; empty = ask your own. |
| `message` | short human-readable hint; the structured fields above are authoritative. |

This is **identical** to the original AI Search tool's contract, so the agent and
its prompt don't change — only the engine underneath did.

## Part J — Glossary (for non-technical stakeholders)

- **Embedding** — a list of numbers representing the *meaning* of text; similar
  meanings produce nearby lists.
- **Cosine similarity / distance** — how close two embeddings point in the same
  direction; the core "are these about the same thing?" measure.
- **pgvector** — a PostgreSQL add-on that stores embeddings and searches them.
- **HNSW** — the index that makes vector search fast on large data.
- **Full-text / BM25 / tsvector** — classic keyword search (exact word overlap).
- **Hybrid search** — combining keyword + vector results (here via RRF).
- **RRF (Reciprocal Rank Fusion)** — a simple, robust way to merge two ranked
  lists without tuning weights.
- **Reranker / cross-encoder (Cohere)** — a model that reads the query and a
  candidate together and scores true relevance; more accurate than vector
  similarity, used on the shortlist only (because it's heavier per item).
- **Recall / top-1 / MRR** — accuracy metrics: is the right article *found*, is it
  *first*, and how *high* on average.
- **Spread** — our confidence check: is there a clear winner, or a near-tie?
- **Round cap** — the limit on follow-up questions so a conversation always ends.
